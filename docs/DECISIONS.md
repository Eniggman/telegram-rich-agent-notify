# Архитектурные решения: Двусторонний Telegram-мост для Antigravity

## 1. Контроль жизненного цикла: Строгий 1-часовой таймер сессии (Hard 60-min TTL)
* **Проблема:** Бот не должен висеть в памяти вечно и не должен зависеть от привязки к процессам.
* **Решение:** Бот запускается строго по требованию (On-Demand), когда агенту требуется ответ пользователя или отправка запроса. При старте запускается таймер ровно на **1 час (3600 секунд)**. По истечении 60 минут бот самостоятельно и чисто завершает работу (os._exit(0)), освобождая память, порты и удаляя lock/pid файлы. При необходимости агент автоматически поднимает свежую сессию снова.

## 2. Формат взаимодействия: Текстовый ввод как приоритетный сценарий
* **Решение:** 
  * Основной сценарий работы — свободный ввод текста со смартфона. Пользователь пишет ответ своими словами в чат бота (например, «делай вариант 2», «ку», «подожди»).
  * Бот моментально перехватывает сообщение, привязывает к активному запросу, отправляет пользователю квитанцию ✅ Принято, передал агенту и передаёт текст в PowerShell.
  * Инлайн-кнопки остаются опциональным вспомогательным инструментом (-Options), но не являются обязательными.

## 3. Безопасность и разграничение доступа (Access Control)
* **Решение:** 
  * Строгая фильтрация по chat_id из 	elegram.json через декоратор @authorized_only. Запросы от посторонних аккаунтов отбрасываются и логируются как инциденты безопасности.
  * Криптографические UUIDv4 для всех идентификаторов запросов (исключает Path Traversal).
  * Экранирование HTML-спецсимволов (html.escape) в сообщениях для защиты от XSS и разрыва разметки Telegram.

## 4. Межпроцессное взаимодействие (IPC) и атомарность
* **Решение:**
  * Файловый IPC в каталоге ipc/ с атомарной записью через .tmp файлы (atomic_write_json).
  * Кэширование обработанных запросов (completed_requests) для предотвращения дублирования сообщений.
  * Дисковая TTL-очистка устаревших файлов запросов.

## 5. Расширенное форматирование Rich Messages (Bot API 10.1+) и гарантированная доставка
* **Проблема:**
  * Большие отчёты и системные логи обрезались лимитом 4 096 символов в обычном sendMessage.
  * Длинные логи загромождали чат пользователя на смартфоне.
  * Чужие сторонние скиллы из интернета несут риск инъекций и вредоносного кода.
* **Решение:**

  * Создан полностью изолированный, проверенный и чистый форк спецификации Rich Message в `tg-rich-post` без сторонних зависимостей.
  * Поддержан прямой метод Bot API 10.1+ `sendRichMessage` с лимитом до 32 768 знаков.
  * Подробности и логи по умолчанию прячутся в сворачиваемый блок `<details><summary>...</summary>...</details>` или раскрываемую цитату `<blockquote expandable>`.
  * Реализован двухуровневый Fallback:
    1. Если `sendRichMessage` недоступен или возвращает ошибку, тег `<details>` автоматически конвертируется в `<blockquote expandable>` с отправкой через `sendMessage`.
    2. Если объём данных превышает 32 000 символов или указан флаг `-AsDocument`, скрипт отправляет краткую карточку-сводку в чат, а полный текст автоматически прикрепляет отдельным файлом `.log` через метод `sendDocument` с использованием .NET `HttpClient` (`multipart/form-data`).
  * Файлы скриптов сохранены в кодировке UTF-8 с BOM для 100% совместимости как с Windows PowerShell 5.1, так и с PowerShell 7 (pwsh).
